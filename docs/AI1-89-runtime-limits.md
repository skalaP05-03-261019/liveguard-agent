# #89: 공유 런타임 진입 제어, 모델 할당량 및 보존 정책

## 배포 경계와 기본값

[기존 #58/#60/#74 런타임 안내](AI1-10-task-runtime.md)에 설명된 대로,
API 전용 접수 프로세스와 독립 `python -m app.worker` 프로세스를 동일한
PostgreSQL Inbox 및 체크포인트 데이터베이스에 연결해 배포한다.
Backend 코드, 승인 권한 또는 보수적인 변경 복구 방식은 바꾸지 않는다.
아래 값은 **서비스 내부의 상한이며, 공급업체 할당량을 보장하지 않는다**.

| 설정 | 기본값 | 적용 범위 |
|---|---:|---|
| `AGENT_WORKER_GRAPH_CONCURRENCY` | 2 | 워커 ID |
| `AGENT_GRAPH_CONCURRENCY` | 4 | 공유 Inbox 스키마 |
| `AGENT_MODEL_CONCURRENCY` | 4 | 해당 스키마의 모든 할당량 그룹 |
| `AGENT_INBOX_CAPACITY` | 10000 | 비종료 작업 |
| `MODEL_CONCURRENCY` | 4 | 할당량 그룹 (sLLM은 명시적으로 1로 설정 가능) |
| `MODEL_RPM` / `MODEL_TPM` | 30 / 60000 | 할당량 그룹, 최근 60초 기준 |
| `MODEL_MAX_INPUT_TOKENS` / `MODEL_MAX_OUTPUT_TOKENS` | 12000 / 2000 | 시도별 |
| `MODEL_TIMEOUT_SECONDS` | 30 | 모델 시도별, 공유 진입 대기 시간 제외 |

워커 ID는 프로세스마다 고유해야 한다. ID를 재사용하면 두 슬롯 제한을 공유하지만,
소유권을 공유하는 것은 아니다. 각 작업 선점에는 여전히 별도의 lease token이 있다.
상한을 공유해야 하는 모든 프로세스에는 **하나의** Inbox 스키마를 사용한다.
스키마나 데이터베이스가 다르면 분산 할당량을 공유하지 않는 별도 클러스터다.

시작 시 공유 런타임 설정 네 가지를 `agent_inbox.runtime_settings`에 저장하고
검사한다. 설정이 서로 다르면 fail closed 방식으로 시작을 거부한다. 각 할당량의
RPM/TPM/동시성 정책도 저장된 행과 대조한다. 설정을 변경할 때는 모든 워커의
작업 선점을 중지하고 진행 중인 작업을 비우거나 fencing한 뒤, API와 워커의
새 설정을 조율하고 재시작 전에 해당 정책 행을 명시적으로 갱신한다.
같은 공급업체 할당량에 대해 스키마나 그룹 이름을 바꿔 검사를 우회하지 않는다.

SQLite 통합 런타임은 단일 호스트 실행 방식을 유지하면서 동일한 접수 용량
규칙을 사용한다. 분산 Graph/모델 진입 제어와 메트릭 엔드포인트는 공유
PostgreSQL 워커에 적용되며, 독립 초안·후보 기능, 직접 SDK 호출 또는 레거시
SQLite 호출자에는 적용되지 않는다.

## 선점 전 스케줄링 및 신뢰할 수 있는 방송 범위

advisory transaction lock은 짧은 진입 허가 결정을 직렬화한다. 유효한
RUNNING lease가 Graph 슬롯이다. 클러스터 및 워커 용량은 작업 선점 **전에**
thread 배타 처리 및 새 lease token 발급과 원자적으로 검사한다.
유휴 워커는 초과 작업을 선점해 RUNNING 상태에서 기다리지 않고 QUEUED 상태로
둔다. 워커마다 서로 독립된 실행 레인이 두 개 있다. WAITING_REVIEW, UNKNOWN
및 종료된 작업은 Graph 슬롯을 점유하지 않는다. 만료된 lease는 기존의 보수적인
started/mutation/checkpoint 규칙에 따라 복구할 수 있다.

`TaskEnvelope`는 인증된 신뢰 경로의 BE 생산자가 제공하는 선택 UUID `liveId`를
받는다. 생산자는 고정된 사건/체크포인트와 일치하는 실제 방송 UUID를 **run 및
resume 모두에** 일관되게 제공해야 한다. 최초 실행 시 기존 사건 조회 결과와
대조하고, 검토 재개 시 체크포인트 범위를 확인한다. 이는 스케줄링 메타데이터일
뿐, 권한 부여 수단이나 BE 바인딩의 대체재가 아니다. Agent가 BE dispatcher나
envelope 구현을 임의로 만들거나 수정하지 않는다.

기존 Agent envelope에는 `liveId`가 필요하지 않다. 문서화된 BE 초안은 운영 중인
생산자가 이를 전송한다는 증거가 아니다. `liveId` 누락은 명시적으로
`legacy:missing-live-id`에 대응한다. **`threadId`, 작업/사건 ID, 채널 이름 또는
채팅 내용으로 방송을 추정하지 않는다.** 호환성을 우선하므로 접수 전에 새 BE
조회는 요구하지 않는다. 따라서 서로 다른 레거시 방송은 한 버킷을 공유하며,
생산자가 신뢰할 수 있는 `liveId`를 제공하기 전에는 방송별 공정성을 보장할 수
없다. `liveId`가 누락된 경우 정규화에서 제외해 업그레이드 전 멱등성 지문을
유지한다.

실행 가능한 방송은 가장 최근에 허가된 시점이 오래된 순서로 라운드 로빈 처리하고,
방송 내에서는 FIFO 순서를 따른다. 다른 방송에 실행 가능한 대기 작업이 있을 때
한 방송이 기본 4개 슬롯 중 점유할 수 있는 수는 최대 2개다. 다른 방송의 대기
작업이 없으면 4개를 모두 사용할 수 있다. 대기열이 비어 있던 방송의 작업이 새로
도착해도 이미 실행 중인 작업을 선점하지 않는다. 다음에 해제되는 슬롯부터
공정하게 고려한다. 지연 재시도 중인 작업과 앞선 작업에 막힌 작업은 실행 가능한
대기 작업으로 보지 않는다. 클러스터 동시성 설정이 4가 아니면 경합 시 할당량은
`max(1, concurrency // 2)`다.

## 모델 식별, 진입 제어 및 사용량 집계

OpenAI 사용은 계속 명시적 선택 사항이다. `MODEL_PROVIDER=openai`와 명시적인
`MODEL_NAME`, API 키가 필요하다. `MODEL_BASE_URL`은 별도로 설정할 수 있다.
OpenAI 호환 sLLM 엔드포인트에는 다음을 사용한다.

```dotenv
MODEL_PROVIDER=openai-compatible
MODEL_BASE_URL=http://your-trusted-sllm:8000/v1
MODEL_NAME=your-deployed-model
MODEL_API_KEY=your-service-credential
MODEL_QUOTA_GROUP=your-sllm-entitlement
MODEL_CONCURRENCY=1
```

sLLM에는 GPT 모델, 할당량, 토크나이저 또는 엔드포인트 프로필을 자동 선택하지
않는다. 해당 엔드포인트는 Chat Completions 함수 호출과 요청된 출력 토큰 상한을
지원해야 한다. 메트릭 응답에는 공급자 인증 정보를 포함하지 않는다.

`MODEL_QUOTA_GROUP`이 없으면 공급자/모델/엔드포인트로부터 식별자를 계산한다.
그룹을 명시하면 **별칭과 엔드포인트를 넘어서** 그 그룹을 기준으로 삼는다.
같은 할당량을 공유하는 모든 별칭은 동일한 그룹과 RPM/TPM/동시성 설정을 사용해야
한다. 서로 독립적인 엔드포인트에는 다른 그룹을 사용한다. 저장되는 키는 URL이나
인증 정보가 아니라 해시다. 공유 워커에 주입하는 모델은 `quota_key`, `limits`
(`ModelLimits`) 및 `estimate_input_tokens(messages, tools)`를 제공할 수 있다.
그렇지 않으면 문서화된 공유 `injected-model` 그룹과 기본 추정치를 사용한다.

공급자 호출을 **시도할 때마다** 짧은 소유권 확인 트랜잭션으로 요청 하나, 추정
입력 토큰과 최대 출력 토큰의 합, 클러스터 모델 슬롯 및 그룹 슬롯을 예약한다.
프로세스 간에 최근 RPM/TPM과 그룹 cooldown을 원자적으로 검사한다. 예약량에는
직렬화된 system/user 메시지, 누적된 도구 응답, 도구 스키마와 프레이밍이 포함된다.
기본 추정식은 `ceil(ASCII characters / 3 + non-ASCII characters * 2) + 256`이다.
이는 서비스 내부 추정치이지, **공급자 토크나이저의 정확한 값이나 보장된 상한이
아니다**. 정확한 토큰 진입 제어가 필요하면 공급자별 추정기를 제공한다.

입력이 너무 크면 조용히 줄이지 않고 `MODEL_CONTEXT_LIMIT`으로 거부한다. 기존의
명시적인 `[TRUNCATED]` 표시 및 불완전한 문맥 거부 동작은 유지한다. 출력은
2000토큰 상한으로 요청한다. 설정한 상한을 넘는 것으로 확인된 사용량은 결과로
변환하지 않고 거부한다.

음수가 아닌 정수로 확인된 입력/출력 사용량은 예약량에 반영한다. 모델 출력이
잘못된 경우에도 확인된 사용량은 반영한다. 사용량을 알 수 없는 경우(시간 초과,
전송 오류, 취소)에는 최근 집계 기간 동안 전체 토큰 예약량을 유지한다.
실패한 시도를 포함한 모든 시도는 RPM을 소비한다. 모델 동시성 슬롯은 시도가
끝나면 해제한다. 최근 집계 기간보다 오래되고 비활성 상태인 예약 행은 진입
제어 중 정리하지만, 활성 상태이거나 집계 기간 내에 있는 행은 삭제하지 않는다.

진입 대기 시간은 Harness 활성 실행 시간과 모델 timeout에 포함되지 않는다.
일반 작업 heartbeat는 할당량 대기와 backoff 중에도 계속된다. 모델 슬롯은 같은
작업 lease/token에 묶이고 heartbeat로 갱신된다. 오래된 소유자는 새 모델 호출을
허가받거나 체크포인트를 쓰거나 후속 도구/변경 작업을 승인할 수 없다.
모델/도구 호출, 할당량 대기 또는 backoff 중에는 데이터베이스 트랜잭션을 열어
두지 않는다. 체크포인트 커밋 시에는 **동일한** 짧은 데이터베이스 트랜잭션 안에서
Inbox 소유권 행도 확인한다. 종료 시에는 취소에 저항하는 의존성이 있더라도
취소 전에 모든 활성 레인을 fencing한다.

## 재시도, 백프레셔 및 관측성

SDK 재시도는 계속 비활성화한다. Harness는 호출마다 최대 **2회의 추가 모델
재시도**(총 3회 시도)를 관리한다. 지수 backoff는 2를 밑으로 하는 지수 방식으로
계산하고, 최대 30초에 제한하며 제한된 jitter를 더한다(지수 지연과 jitter의 합도
최대 30초). `Retry-After`가 초 단위 값이나 HTTP 날짜로 제공되면 상한보다 길더라도
최소 대기 시간으로 적용한다. 429 응답은 공유 할당량 그룹의 cooldown도 연장한다
(최소 2초). 다른 워커/별칭도 이 제한을 우회할 수 없다. 재시도할 수 없는 출력/
인증/바인딩 오류는 재시도하지 않는다.

Graph 실행마다 추가 모델 재시도는 최대 **4회**다.
`harness_budget.modelRetryCount`는 Graph 상태에 예산을 보존한다. 또한 소유 중인
Inbox 작업에서 재시도하기 **전에** `model_retries`를 영속적으로 증가시킨다.
따라서 노드 체크포인트 전에 프로세스가 중단되어도 재시도 횟수가 초기화되지
않는다. 이 값은 Inbox `attempts` 및 작업 선점/복구를 관리하는
`AGENT_WORKER_MAX_ATTEMPTS`와 별개다. 기존의 모델 최대 8회 시도 및 도구/활성 시간
예산은 그대로 유지한다.

접수 시 QUEUED/RUNNING/WAITING_REVIEW/UNKNOWN 상태의 작업 수를 원자적으로
집계한다. 용량을 초과하면 **새 작업**에 다음 응답을 반환한다.

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 10

{"detail":{"code":"INBOX_CAPACITY_EXCEEDED"}}
```

동일한 중복 요청은 계속 200을 반환하고 상태 조회도 가능하다. 내용이 충돌하는
중복 요청은 계속 409를 반환한다. 용량 초과 거부 시 thread를 바인딩하거나 작업을
생성하지 않는다. 재개도 새 작업이므로 용량이 찬 경우 거부될 수 있다.

`GET /agent/metrics`는 작업 요청과 **동일한 ****** 인증을 사용한다.
집계된 JSON만 반환한다. 여기에는 queued/running/waiting-review/unknown 개수,
가장 오래된 대기열 및 모델 진입 대기 시간, 최장 RUNNING 시간, 활성 모델 호출,
만료 lease 게이지, 모델 대기/제한/timeout/재시도/429 카운터, lease 만료/복구
카운터가 포함된다. `wait_severity`는 대기열 또는 모델 대기 시간이 30초일 때
`warning`, 120초일 때 `critical`이다. Lease 카운터는 관측된 만료/회수 시도
횟수이며 게이지에는 아직 회수하지 않은 만료 lease도 포함된다. 메트릭에는
envelope, 방송/작업 ID, 토큰/인증 정보 또는 원본 프롬프트가 포함되지 않는다.
기존 허용 목록 기반 Harness 로그에는 안전한 호출별 사용량과 시간이 계속
기록된다.

## 보존은 명시적으로 관리

Inbox 작업, thread 바인딩, 멱등성 지문, 해결되지 않은 UNKNOWN/검토 기록,
할당량 집계 또는 카운터를 대상으로 **자동 삭제**, TTL 정리 또는 조용한 제거를
수행하지 않는다. 종료된 작업은 중복 요청 영수증을 삭제하지 않고 접수 용량만
해제한다. 오래된 할당량 예약은 최근 집계 기간이 지나면 RPM/TPM을 더 이상
소비하지 않지만, 예약 행 자체를 삭제하는 것은 아니다.

운영자는 데이터베이스 증가량을 모니터링하고 백업/아카이브 및 보존 절차를
명시적으로 정해야 한다. 용량 확보만을 위해 멱등성 기록을 삭제하지 않는다.
삭제하면 중복 제재를 허용할 수 있다. UNKNOWN/검토 결과는 기존의 신뢰된 복구/
승인 절차에 따라 해결한다.

`tests/test_runtime_limits.py`는 실제 PostgreSQL 연결, 작업 선점 및 용량 경쟁,
실제 워커/Graph 두 개가 동시에 네 건의 호출에 도달하는 상황, heartbeat/drain,
부하가 높은 방송과 낮은 방송 간 공정한 허가, 공유 RPM/토큰/cooldown, 대기 중
lease fencing, 독립적인 재시도 집계 및 인증된 메트릭을 검증한다.
기존 공유 워커/체크포인트 테스트와 함께 `AGENT_TEST_CHECKPOINT_DB_URL`을 설정하고
`AGENT_TEST_INBOX_DB_URL`로 실행한다. 테스트는 격리된 스키마와 모의 모델/BE
전송을 사용하며, 실제 공급자 할당량이나 실제 제재 동작은 사용하지 않는다.
