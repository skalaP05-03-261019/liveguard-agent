## 1. 역할 분담 요약

Phase 2는 기획서의 **욕설 없는 혐오·지역비하 탐지, 고객사별 검토 프로필, 운영자 판단 근거, 역할 중립 채팅 요약** 방향으로 진행합니다.

두 사람의 주담당을 다음과 같이 나눕니다. 각자 맡은 모듈의 평가·테스트·실패 분석도 함께 담당합니다.

| 담당 | 개발의 중심 | 주요 책임 |
|---|---|---|
| 태관 | 어떤 발언을 조사할 것인가 | UnSmile 데이터 선별·공통 평가셋·탐지 baseline, 후보 판별, 고객사 프로필별 탐지 기준, BE 협의·Gateway·통합 연결 |
| 세원님 | 왜 문제이며 어떤 근거가 있는가 | 문맥 조사, 정책 검색·근거 연결, 운영자에게 전달할 조사 결과, 조사 품질 평가, 역할 중립 채팅 요약과 해당 평가 |

세원님은 단순 요약 기능 담당이 아니라, **탐지된 후보를 설명 가능한 판단으로 만드는 Agent의 핵심 조사 기능**을 담당합니다.

기획 방향은 위 제안서를 따릅니다. 신규 정책 유형·API 필드·실시간 예산 등 세부 계약은 관련 담당자와 합의한 뒤 구현합니다.

## 2. 전체 처리 흐름과 인계 지점

```text
실시간 채팅
  → 기존 BE 규칙 처리
  → 태관: 추가 후보 판별·프로필 적용
  → BE: HELD·사건·권한 검증된 증거 준비
  → 세원님: 문맥·정책 조사와 근거 있는 AI 제안
  → 태관: BE 판정 제출·결정/재개 연동
  → 운영자 최종 결정
  → BE 실제 조치·FE 상태 갱신
```

- 탐지 후보는 위반 확정이 아닙니다.
- BE의 사건·snapshot·정책 버전·대상 메시지를 정본으로 사용합니다. 후보 판별 결과만으로 사건이나 증거를 만들어내지 않습니다.
- 이번에 추가하는 의미 기반 문맥 후보는 정상·위반·보류 모두 기존 사람 결정 흐름을 따릅니다.
- 기존 명확한 욕설·링크의 BE 규칙 확정, PII 별도 경로, 별도 강퇴 승인 절차를 일괄 변경하지 않습니다.
- 정확한 후보 호출 위치와 공개 전/후 처리, 시간 초과 시 노출 상태는 BE 담당자와 태관이 맞춥니다.

## 3. 세원님 담당 A — 후보의 문맥 조사

### 목적

태관의 탐지 모듈에서 발견한 후보를 받아, 실제 주변 대화와 정책을 조사합니다. 단어가 포함됐다는 사실만으로 판단하지 않고 **대상·표현·문맥·불확실성**을 구분합니다.

### 개발할 내용

1. **지칭 대상 확인**
   - 개인, 지역·사회적 집단, 게임 팀, 방송 내용 등을 구분합니다.
   - 닉네임·호칭과 실제 대상의 연결은 제공된 증거로 확인합니다.
   - 문맥에 없는 개인이나 집단을 추측해 만들지 않습니다.
2. **표현의 의미 조사**
   - 집단 일반화, 열등성 주장, 배제, 조롱, 반복 공격 등의 근거 표현을 찾습니다.
   - 정상적인 지역·집단 언급이나 방송에 대한 비판과 구분합니다.
3. **앞뒤 문맥 확인**
   - 다른 발언의 인용, 비하에 대한 반박, 자기 지칭, 대화 주제를 확인합니다.
   - 반복 공격을 주장하려면 실제로 조회한 메시지의 반복 근거가 있어야 합니다.
4. **불확실성 처리**
   - 판단에 필요한 대상·맥락·사실이 부족하면 `NEEDS_REVIEW`와 `missingFacts`를 사용합니다.
   - 정책·도구·의존성 오류를 정상 발언 판정으로 바꾸지 않습니다. 실제 오류와 사실 부족에 따른 보류를 구분합니다.

### 대표 검증 사례

| 상황 | 확인할 행동 |
|---|---|
| 욕설 없이 특정 지역 전체를 열등하게 표현 | 집단과 비하 표현을 확인하고 합의된 정책으로 조사 |
| 지역별 맛집·여행 정보를 질문 | 지역명 등장만으로 혐오라고 판단하지 않음 |
| “그런 지역비하는 하지 맙시다” | 비하를 반대하는 표현인지 문맥 확인 |
| “역시 저쪽은 다 똑같네” | 대상이 확인되지 않으면 임의로 집단을 특정하지 않음 |
| 특정 사용자에게 반복적인 조롱 | 실제 대상·주변 메시지·반복 근거를 사용 |

위 표는 평가 설계 예시입니다. 실제 기대 판정은 팀 정책과 전체 문맥을 검수해 확정합니다.

### 산출물·완료 조건

- 조사 프롬프트와 필요한 조사 로직
- 정상·위반·보류의 판단 근거와 부족한 사실
- 대상만 판정하고 주변 메시지는 근거로 사용하는 검사
- 조회하지 않은 메시지·정책을 근거로 생성하지 않는 검사
- 문맥이 부족한 사례에서 근거 없는 단정이 발생하는지 평가한 결과

## 4. 세원님 담당 B — 정책 검색과 신규 탐지 유형의 근거 연결

### 목적

후보 탐지의 위험 신호를 **서비스에서 승인한 정책 기준**으로 조사할 수 있게 연결합니다. UnSmile 분류와 서비스의 위반 확정 유형을 구분합니다.

### 개발할 내용

- 기존 정책으로 조사할 수 있는 사례와 신규 정책 합의가 필요한 사례를 구분합니다.
- 지역비하·집단 혐오·배제 표현에 대한 위반 조건과 정상 예외의 초안을 정리합니다.
- 검색 결과뿐 아니라 해당 조항의 원문·버전을 확인하고 실제로 조회한 정책 ID를 연결합니다.
- 관련 정책이 검색되지 않는 경우와, 검색됐지만 판단을 뒷받침하지 못하는 경우를 구분합니다.
- 신규 정책의 원문·색인·Agent 소비 버전을 맞춥니다. 버전 불일치를 임의의 문구나 구버전 근거로 보완하지 않습니다.
- 검색 개선은 확인된 실패를 대상으로 적용하고, 변경 전후 같은 사례로 비교합니다.

### 먼저 작성할 대응표

| 탐지 신호·사례 | 적용 가능한 기존 정책 | 새 합의가 필요한 부분 | 판단에 필요한 사실 |
|---|---|---|---|
| 지역·집단 일반화와 비하 | 기존 정책 검토 후 기재 | 신규 유형·정상 예외·제재 연결 | 지칭 집단, 인용 여부, 주변 문맥 |
| 개인을 향한 반복 조롱 | 기존 괴롭힘 정책 검토 | 집단 혐오와의 구분 | 대상 식별, 실제 반복 근거 |
| 변형 욕설 | 기존 욕설 정책 검토 | 사전 확정 또는 문맥 조사 경로 | 표현 의미, 실제 발언 |
| 정상 언급·반박·자기 지칭 | 해당 정상/보류 기준 검토 | 유형별 예외 기준 | 발언 목적과 앞뒤 대화 |

### 지켜야 할 경계

- 데이터셋의 ‘지역’ 라벨을 곧바로 서비스의 위반 확정으로 사용하지 않습니다.
- 집단 혐오를 기존 `HARASSMENT`에 무조건 편입하거나 허용되지 않은 enum을 출력하지 않습니다.
- 신규 유형·집계·제재·BE/FE 계약 변경은 팀 합의 후 반영합니다.
- 유사 댓글이 검색됐다는 이유만으로 위반을 확정하지 않습니다. 댓글 사례와 정책 근거는 다릅니다.
- 현재 규칙 확정에 적용되는 욕설 인용·제지 정책에 새 예외를 임의로 추가하지 않습니다.

### 산출물·완료 조건

- 탐지 신호와 정책의 대응표, 정책 보완 초안
- 정책 검색·원문·버전 연결 코드와 회귀 검사
- 정책을 찾았는지에 대한 검색 평가와, 그 정책을 올바르게 적용했는지에 대한 조사 평가를 분리한 결과
- 운영자가 어떤 정책을 왜 적용했는지 확인할 수 있는 근거

## 5. 세원님 담당 C — 운영자에게 전달할 조사 결과 구성

세원님은 **결과 내용의 생성과 의미**, 태관은 **BE 전달·저장·결정/재개 어댑터**, FE 담당자는 **실제 카드 화면**을 담당합니다.

### 결과에 담을 내용

| 정보 | 작성 기준 |
|---|---|
| AI 제안 | 정상·위반·확인 필요. 사람의 최종 결정과 구분 |
| 문제 표현 | 실제 대상 메시지에서 판단과 관련된 표현 |
| 대상 | 확인한 개인·집단 또는 대상 미확인 |
| 문맥 근거 | 실제로 제공·조회된 근거 메시지 ID |
| 정책 근거 | 실제 조회한 정책 ID와 버전 |
| 판단 이유 | 운영자가 이해할 수 있는 짧고 구체적인 설명 |
| 부족한 사실 | 확정에 필요한 추가 정보 |

기존 조사 출력 계약을 우선 사용합니다. 위 정보가 모두 새 JSON 필드를 요구하는 것은 아닙니다. 필드 추가가 필요하면 태관·BE·FE와 먼저 합의합니다.

### 역할·공식 여부의 해석

- `authorRole=UNKNOWN`은 현재 역할 미확인이며 VIEWER로 바꾸지 않습니다.
- `isOfficialOperator=false`는 공식 운영자로 확인되지 않았다는 뜻이지, 시청자나 사칭자 확정이 아닙니다.
- 현재 역할을 사건 당시 역할로 소급하지 않습니다.
- 역할 정보와 `security-facts`는 출처·대상·시점을 확인하고 서로 덮어쓰지 않습니다.
- 이 내용은 기존 Agent #57의 지침을 유지·회귀 확인하는 범위입니다.

### 완료 조건

“불쾌한 표현입니다”로 끝내지 않고, **어떤 표현이 누구에게 어떤 의미로 쓰였다고 보았는지** 설명할 수 있어야 합니다. 제재 기간이나 실행 명령은 조사 모델이 만들지 않습니다.

## 6. 세원님 담당 D — 역할 중립 채팅 요약

### 우선순위

요약 기술의 최소 동작 흐름은 구현합니다. P0 후보→조사→사람 결정 연결 및 baseline과 우선순위를 조정해 P1로 병행합니다. 이용 역할·제공 시점·화면 위치는 추후 결정하며, 타깃 미정을 이유로 공통 모듈 개발을 미루지 않습니다.

### 목적과 출력

스트리머의 최근 대화 점검 또는 시청자의 이전 대화 파악에 활용할 수 있도록, 지정한 시간 구간의 채팅을 요약하는 공통 모듈을 구현합니다. 둘 중 누가 사용할지는 미정입니다. 초기 MVP의 입력은 PUBLIC 메시지를 기본 범위로 하고 서버가 호출자 권한을 검증해야 합니다. 요약 내용은 다음과 같습니다.

- 주요 대화 주제
- 사람들이 주고받는 질문·추천
- 아직 결론이 나지 않은 사항
- 대상 시간, 생성 시각, 근거 메시지 참조

이는 채팅 흐름 요약이며 영상·음성을 분석한 방송 내용 요약이 아닙니다.

### 개발할 내용

- 서버가 호출자 권한·공개 범위를 검증한 메시지와 시간 구간을 입력받는 역할 중립 요약 모듈
- 요약 프롬프트·출력 규격·검증
- 근거 없는 문장과 잘못된 공식 발언화를 줄이는 처리
- 대화 부족, 모델 오류, 시간 초과의 구분
- 근거 메시지·범위·버전 등 캐시와 무효화에 필요한 정보 제공
- 근거가 숨김·삭제·정정됐을 때 기존 요약을 계속 사용하지 않도록 하는 소비자 처리

### 태관·BE와의 협업 경계

- 공개 메시지 조회·권한 필터·업무 API 연동은 태관이 BE 담당자와 조율합니다. 이용 역할은 추후 합의하며, 스트리머라는 이유로 비공개 원문을 자동 포함하지 않습니다.
- 캐시 키와 무효화 이벤트·재생성 연결은 세원님이 요구사항을 제시하고 함께 계약을 맞춥니다.
- 작성자에게만 보이는 HELD/HIDDEN, 비공개 운영자 정보는 공용 요약에 넣지 않습니다.
- 요약 모듈이 권한 검사를 대신하거나 업무 DB에서 임의로 전체 채팅을 읽지 않습니다.

### 완료 조건

| 사례 | 확인할 결과 |
|---|---|
| 충분한 공개 대화 | 원문이 뒷받침하는 주제·질문 요약과 근거 |
| 대화 없음·부족 | 요약할 대화가 부족함을 표시 |
| 비공개 메시지 포함 상황 | 해당 메시지를 공용 요약의 입력·근거에서 제외 |
| 시청자의 추측 | 스트리머의 공식 사실·결정으로 바꾸지 않음 |
| 근거 메시지의 공개 상태 변경 | 합의한 무효화 계약에 따라 오래된 요약 제공 중단 |
| 모델·외부 시스템 오류 | 성공 요약을 만들어내지 않고 사용 불가 상태 전달 |
| 채팅 안에 요약 명령·지시 삽입 | 채팅을 데이터로 취급하고 실행 지시로 따르지 않음 |

## 7. 평가 분담

전체 평가를 한 사람이 맡지 않습니다. 공통 평가셋과 버전은 함께 고정하되 각 모듈의 실제 결과는 담당자가 측정합니다.

| 태관 담당 | 세원님 담당 |
|---|---|
| 후보 탐지 baseline·누락·오탐 | 같은 후보의 문맥 판단 품질 |
| 프로필별 후보 수와 탐지 기준 | 정책 검색·인용의 적절성 |
| BE 실제 전달·카드 도달 지연 | 적절한 보류·부족한 사실 출력 |
| Gateway·입출력·통합 경로 검사 | 조사 모듈 자체 오류·예산·회귀 검사 |
| 전체 결과 취합·실제 연동 확인 | 요약 사실성·공개 범위·근거·실패 처리 |

세원님은 다음 기록을 남깁니다.

1. 변경 전 모델·프롬프트·정책·평가셋·실행 환경
2. 사례별 입력, 기대 결과와 근거, 실제 출력, 충족 여부
3. 바꾼 요소와 변경 이유
4. 같은 사례의 재측정 결과
5. 남은 실패·원인·다음 조치, 처리 시간·호출량

검색 적중률과 최종 판단 품질은 별도로 보고합니다. 실제 모델 평가, scripted model/HTTP 대역을 사용하는 통제 검사, 실제 BE·화면 연동 증거를 구분합니다. 개선에 사용하지 않는 확인용 사례는 따로 보존합니다.

## 8. 착수 전에 둘이 합의할 계약

팀 작업표에서는 방송별 설정을 레벨형·항목형·자연어형 중 협의 대상으로 관리합니다. 태관의 프로필 업무는 방식 비교와 후보 판별 기준을 포함하며, 3단계 UI 확정으로 간주하지 않습니다. 커뮤니티 은어는 조사 예정이며 수집·사용·문맥 검수 조건을 먼저 맞춥니다. 고객사 정책 조항 기반 설명은 차별화 후보로 함께 검토하되 실제 고객사 문서 등록·승인·색인 격리는 별도 계약으로 둡니다.


다음 항목을 먼저 문서와 예시 데이터로 맞춥니다. 아래는 확인할 정보 목록이며 확정 DTO나 새 API 명세가 아닙니다.

| 인계 지점 | 합의할 정보 |
|---|---|
| 탐지 → BE 사건 생성 | 고객사·방송 범위, 원본 메시지, 후보 신호·표현, 프로필 버전, 실패 처리 |
| BE 증거 → 조사 | 사건·snapshot·증거 버전, 정책 버전, TARGET/CONTEXT 구분, 권한 검증된 사실 |
| 조사 → 태관 어댑터 | 메시지별 판정·정책·증거·이유·부족한 사실, 오류 구분 |
| 권한 검증 채팅 조회 → 요약 | 호출자 권한·고객사·방송·시간창·공개 범위, 메시지 참조·버전, 부족/오류 상태 |
| 근거 변경 → 요약 무효화 | 변경 이벤트·근거 식별·버전, 캐시 무효화·재생성 처리 |

공통 스키마·Graph 진입점·설정·공용 테스트 파일을 수정할 때는 먼저 변경 범위를 공유합니다. 각자 독립 모듈로 작업하고, 공통 계약 변경은 함께 검토합니다. 기존 Harness의 호출 예산·인증·중복 방지·승인·checkpoint를 우회하지 않습니다.

## 10. 최종 인수 체크리스트

- [ ] 후보와 위반 확정을 구분한다.
- [ ] 대상·표현·주변 문맥·정책·부족한 사실을 설명한다.
- [ ] 실제 제공·조회한 근거와 같은 정책 버전만 사용한다.
- [ ] 정의 밖 유형이나 근거 부족을 추측으로 확정하지 않는다.
- [ ] UNKNOWN 역할의 의미와 기존 승인·재개 흐름을 보존한다.
- [ ] 조사 변경 전후를 같은 사례로 비교하고 남은 실패를 기록한다.
- [ ] 요약 공통 기능은 공개 범위·근거·빈 대화·정정·오류 검사를 갖추고 이용 역할을 특정 역할에 하드코딩하지 않는다.
- [ ] 코드·평가·문서가 이슈와 PR로 연결되고 본인 담당 코드를 설명할 수 있다.
- [ ] 태관과의 통합에서 성공·보류·오류 사례를 확인한다.

**우선순위: 문맥 조사 → 정책 근거 → 결과 구성 → 평가·통합 → 공개 채팅 요약.**

핵심 목표는 **탐지된 발언을 단순한 점수가 아니라 운영자가 판단할 수 있는 근거로 바꾸는 것**입니다.
