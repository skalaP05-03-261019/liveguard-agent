# 후보 신호를 활용한 문맥 조사 (#71)

후보 탐지가 넘긴 사건을 조사할 때 후보 신호를 참고하고, 정책 대응표(#69, [`policy-mapping-69.md`](policy-mapping-69.md))의 판단 사실(대상·표현·문맥·정책)을 순서대로 확인하도록 조사기를 확장한다. 결과는 기존 출력 계약 그대로이며, 운영자용 설명은 `reason` 형식으로 정리한다.

## 추가 지침 요약

- **후보 힌트:** 종류와 강도, 탐지기가 적은 부족한 사실만 전달한다. 탐지기의 이유 문장은 넘기지 않는다. 힌트는 확인 관점일 뿐 위반 근거가 아니다.
- **지역비하·집단 혐오 (버전별 절):** 지칭 집단과 정체성 속성 → 열등 단정·배제 주장인지(단순 언급, 정책 비판, 가벼운 고정관념은 아님) → 인용·반박·제지·자조인지 순서로 확인한다. v3.1은 CP-6.1 `NEEDS_REVIEW`(HARASSMENT로 바꾸지 않음), v3.2는 CP-3.3 근거 `VIOLATION` HARASSMENT. 조회는 판단에 필요한 조항 2개까지(EXP-02).
- **개인 공격·변형 욕설:** 대상이 문맥에서 식별되면 CP-3.2, 대상 없는 감탄은 CP-2.2, 식별 불가면 보류.
- **제출 전 확인 (EXP-04):** 출력 검증의 실제 거부 조건만 적는다. 인용할 조항은 먼저 조회, 정상·위반은 조항과 TARGET 메시지 필수, 위반 유형은 인용 조항의 유형, 보류는 조회한 경우에만 조항 인용.
- **분량:** 기본 지침(#106)과 겹치는 설명을 빼고 짧게 유지한다. 모델 입력 한도(추정 12,000토큰, #93) 안에서 조항 조회 결과가 들어갈 자리를 남기기 위해서다.
- **reason 형식:** `대상: … 표현: … 문맥: … 판단: …` 300자 이내.

## 평가

```bash
uv run --locked --env-file .env python -m app.investigation_eval \
  --cases tests/fixtures/phase2/investigation-eval-v2.json \
  --standard v3.2 --investigator phase2 --live --limit 20 --policy-version v3.2 \
  --out local-data/inv-eval-phase2-dev.json --details-out local-data/inv-eval-phase2-dev.details.json
```

- 개발 중에는 `development` 20건만 사용한다. `confirmation` 16건은 최종 비교에서 Phase 1 baseline과 함께 한 번 실행한다.
- 한 번에 지침 하나만 바꾸고, 바꿀 때마다 같은 사례로 다시 잰다. 결과가 나빠진 변경도 기록한다.

### 실험 기록 (개발용 20건, 정답 `AUTHOR_DRAFT`)

같은 모델·같은 사례로 실행했다. 충족 = 판정·유형·기대 조항 인용이 모두 맞은 수. 근거 없는 단정 = 근거 없는 위반 + 근거 없는 정상. 오류는 출력 검증 거부·실행 한도로, 판정으로 바꾸지 않고 따로 센다.

- **EXP-01 → 02:** 조항을 하나씩 다 조회하다 같은 도구 3회 한도에 걸리는 실행 한도 오류가 줄었다.
- **v3.2 통합:** 집단 열등 단정 사례(D-P2-01·02)가 HARASSMENT·CP-3.3으로 정답 처리. 집단 혐오를 개인 괴롭힘 조항(CP-3.2)으로 위반 처리하던 Phase 1 오류가 없어졌다.
- **EXP-03 (미채택, EXP-04로 대체):** 처음 2회(16·16)만 보고 개선으로 판단했으나, 같은 코드로 다시 잰 2회가 12·12였다. 진단 결과 거부 대부분이 "조회하지 않은 CP-2.2를 인용"이었다. CP-2.2 필수 규칙이 EXP-02의 2개 조회 한도와 부딪혀, 모델이 CP-3.3·CP-6.1을 조회한 뒤 CP-2.2를 조회 없이 인용했다. 지침이 길어져 모델 입력 한도 초과(`MODEL_CONTEXT_LIMIT`)도 늘었다(v3.2 지침+도구 설명 추정 9,019토큰 / 한도 12,000).
- **EXP-04:** 지침을 추정 7,797토큰으로 줄이고, 검증 코드의 실제 거부 조건만 적었다(EXP-03의 "reason에 적은 조항이 policyIds에 없으면 거부"는 실제 검증에 없는 조건이라 삭제). 실행 5회 모두 충족 18~19, 오류 1. 한 번에 두 가지(축약, 거부 조건 문구)를 바꿨으므로 각각의 효과는 분리하지 못했다.
- **남은 실패:** v3.1 D-P2-06(변형 욕설)이 HARASSMENT와 PROFANITY를 함께 내면서 CP-3.2만 인용(유형-조항 불일치로 거부). v3.2는 실행마다 다른 사례 1건이 검증 거부 또는 입력 한도 초과, 1회는 가벼운 고정관념(D-P2-08)을 위반으로 판정.
- **변동성:** 같은 코드라도 실행마다 충족 수가 4건까지 달라졌다. 이후 비교는 실행 3회 이상을 기준으로 한다.

### 최종 비교, PM 검수 정답 (2026-10-23, `inv-eval-v3`, `REVIEWED`)

PM(강인서) 검수를 반영한 `investigation-eval-v3.json`으로 아래 실행들을 모델 호출 없이 다시 채점했다(details 재생). PM은 **v3.2 정답**을 검수했고, v3.1 정답은 작성자 초안 그대로다.

- 검수로 바뀐 v3.2 정답: D-P2-01·C02(특정 채팅·방송에서의 배제 요구) 보류, D-P2-08 보류, C05 정상.

- **v3.1 확인용:** Phase 1의 근거 없는 단정은 모두 집단 비하를 개인 괴롭힘(HARASSMENT)으로 위반 처리한 것(C01·C02·C03·C04·C15·C16)이다. Phase 2는 6회 모두 0건으로, CP-6.1 보류로 판정했다.
- **v3.2 확인용:** Phase 1은 판정은 맞아도 정상 판정의 근거 조항이 틀리거나(C07·C12·C14 등) 같은 도구 한도(`EXECUTION_LIMIT`)에 걸렸다. Phase 2는 근거 조항까지 맞았다.
- **정책 변경과 조사기 개선의 구분:** Phase 1 조사기도 v3.2 정책에서는 개발용 충족이 17 → 14~18로 크게 나빠지지 않았다. 집단 비하를 위반으로 보는 Phase 1의 경향이 v3.2의 CP-3.3과 맞기 때문이다. Phase 2의 이득은 v3.1에서 근거 없는 위반 제거, v3.2에서 근거 조항 정확도와 실행 오류 감소로 본다.
- **남은 실패:** C11(`ㅅㅂ`로 시작하는 개인 공격, 6회 중 5회). HARASSMENT와 PROFANITY를 함께 내면서 CP-2.1을 인용하지 않아 검증에서 거부되거나 위반을 놓쳤다. `ㅅㅂ`는 BE 확정 욕설 사전 단어라 정답 유형(HARASSMENT 단독)이 맞는지 PM 검수를 요청했다. 개발용 D-P2-06에서 보인 약점과 같다.
- **비용:** Phase 2는 입력 토큰이 약 1.6배(확인용 v3.1 기준 9.0만 → 14.9만, 16건)다. 사례별 순차 지연 p95는 둘 다 5~7초다.
- **해석 범위:** 정답은 작성자 초안이고 PM 검수 전이다. 검수 후 정답이 바뀐 사례만 모델 호출 없이 다시 채점한다. 실행마다 충족 수가 1~3건 흔들리므로 한 번의 실행값으로 비교하지 않는다. BE 조회는 대역이며 후보 유입(BE 사전·UnSmile) 누락은 이 비교에 포함되지 않는다.
