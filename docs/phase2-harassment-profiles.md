# LIVE:GUARD Phase 2 — 방송별 HARASSMENT 판단 프로필 설계

작성일: 2026-10-23  
상태: 요구사항 합의 및 BE #90 계약 결정 반영. API 응답·오류·구조화된 판단 근거는 BE 명세를 따른다. 기존 활성 v3.2를 덮지 않도록 신규 프로필 계약의 정책 버전은 v3.3으로 구분한다. 승인 정책 커밋·본문 해시 고정과 런타임 구현·배포는 후속 작업이다.

2026-10-26 추가 합의: Phase 2 코드 구현은 중단 상태로 유지하고 설계만 갱신한다.
엄격은 기존 필터의 PASS까지 Agent 전달 대상을 확대하며, 보통·자유는 기존처럼
선별된 의심 후보만 전달한다. 후보 확대의 접수 계약과 가시성 영향은 아래 별도 항목으로 정리하며,
이 문서 수정만으로 BE #90·OpenAPI 또는 운영 정책을 변경·활성화하지 않는다.

## 1. 목적

관리자(스트리밍 플랫폼 운영자)가 방송별로 **HARASSMENT 판단에 적용할 정책 조항의 조합**을 선택한다.
방송 소유자(스트리머)와 담당 moderator는 설정을 조회만 할 수 있다.
단순한 모델 민감도 점수나 제재 강도 조절 기능이 아니다.

선택지는 **엄격 / 보통 / 자유** 세 가지다(`STANDARD`는 기존 문서의 “기본”과 같은 값).
프로필은 HARASSMENT 조항 조합과 Agent 전달 범위를 함께 정한다. Agent는 사건에 적용된 프로필과
정책 원문을 기준으로 조사하며, 기존 운영자 승인과 Backend 조치 경계를 유지한다.

신규 기능 활성화 전 승인된 v3.3 원문과 색인을 별도로 준비한다.

원 제품 제안 중 도배 임계값 등 범용 규제 조절은 이번 범위에서 제외한다.
상대 링크의 정책 본문은 변경될 수 있으므로, 프로필 규칙 추가 후 승인된 정책 커밋과
본문 해시를 고정한다. BE의 `docs/policy/` 및 `contracts/openapi.yaml`에도 공동 반영해야
하며, 본 설계만으로 기존 BE 계약을 대체하지 않는다.
본 문서는 정책 승인·배포·활성화를 의미하지 않는다.

## 2. 적용 범위

| 항목 | 이번 변경 |
|---|---|
| HARASSMENT | 프로필에 따라 적용 조항·Agent 전달 범위 변경 |
| PROFANITY: 금지 욕설·비속어 | 기존 규칙 유지 |
| FLOOD: 도배 | 기존 임계값·재적발 규칙 유지 |
| PHISHING: 링크·사칭 | 기존 기준 유지 |
| PII_EXPOSURE: 개인정보 | 기존 기준 유지 |
| 확정 위반 이력·제재 기간·누적 조건 | 기존 방식 유지 |
| CONTEXT 운영자 결정·별도 KICK 승인 | 기존 방식 유지 |
| BE 후보 필터·처리 경로 | 엄격의 PASS 추가 접수 및 의심 표현 후보화 보완. 기존 경로 우선순위·확정 주체는 유지 |
| 경량 모델·UnSmile·Agent 내부 경량 모델→GPT 구성 | 도입·구성은 이번 합의 범위 밖 |

엄격은 **기존 BE 필터에서 PASS로 분류될 메시지도 전부 Agent 조사 대상으로 접수**한다.
보통·자유는 속도·효율을 우선하여 기존처럼 일부 의심 후보만 Agent에 전달한다.
“욕설 외 전부 전달”은 엄격의 전달 범위를 설명한 표현이며, 링크·도배·개인정보 등
이미 정해진 처리 경로를 CONTEXT로 덮거나 모든 프로필에서 전량 전달한다는 뜻은 아니다.
자유를 선택해도 BE가 금지 욕설·링크로 자동 확정한 결과를 해제하지 않는다.

### 2.1 프로필별 접수·전달 기준

| 기존 BE 필터 결과/경로 | 엄격 `STRICT` | 보통 `STANDARD` | 자유 `RELAXED` |
|---|---|---|---|
| RULE_CONFIRMED (욕설·링크) | 기존 BE 확정 유지 | 동일 | 동일 |
| FLOOD_REVIEW | 기존 도배 처리 유지 | 동일 | 동일 |
| PII_INVESTIGATION | 기존 개인정보 조사 유지 | 동일 | 동일 |
| CONTEXT_REVIEW (공격·사칭 의심) | 기존 CONTEXT 접수·Agent 조사 | 동일 | 동일 |
| PASS | 전부 Agent 조사 대상으로 추가 접수. 기존 CONTEXT 사건 경로 재사용을 기준으로 계약 보완 | PUBLIC·Agent 미호출 유지 | PUBLIC·Agent 미호출 유지 |

엄격의 추가 접수는 탐지 누락을 줄이기 위한 조사 범위 확대이지 품질 향상의 보장이 아니다.
처리량·지연·비용·운영자 검토량 증가를 수용·측정한다. Agent 내부의 경량 모델 선별과
GPT 조사 구성은 이 접수 계약과 분리하며 이번 문서에서 새로 지정하지 않는다.
보통·자유의 PASS 뒤에 경량 검사를 의무 추가하거나 그 검사의 모델·임계값을 정한 합의도 아니다.

### 2.2 시연에서 놓친 표현의 후보 사전·정규화 보완 검토

최신 main의 `attack-terms.txt`(dict-v3)는 정규화 후 부분 일치로 비교한다.
`한남충`은 있지만 `한남들`은 없고, `수준이 낮`은 있지만 `수준이 너무 낮`은 포함하지 않는다.
norm-v1은 NFKC·소문자·공백 축약·반복 문자 축약만 하며 조사·부사 삽입을 제거하지 않는다.
따라서 아래 사례의 PASS는 Agent 조사 누락이며, 이 결과가 정책상 정상이라는 뜻은 아니다.

| 시연 입력 | 누락 원인 | 후보화 보완 검토 범위 |
|---|---|---|
| `한남들 개많네` | 사전의 `한남충`과 다른 표현 | `한남들` 등 확인된 비하 용례의 어형을 공격 후보 사전에 추가 검토. `한남` 단독 전역 부분 일치는 지명·기관명·인용 오탐을 함께 검수 |
| `그 지역 사람들은 수준이 너무 낮아` | `수준이 낮` 사이에 부사 삽입 | 시연용으로 `수준이 너무 낮` 등 확인된 변형을 우선 검토. 일반화는 집단 지칭과 열등 단정의 제한된 조합 규칙으로 별도 검수 |

- 후보화는 CONTEXT_REVIEW·Agent 조사 대상 선정일 뿐 PROFANITY나 HARASSMENT 자동 확정이 아니다.
- 두 입력은 세 프로필 모두 조사 후보가 될 수 있지만 자유에서는 CP-3.3만으로 위반을 확정하지 않는다.
  `그 지역`의 실제 대상이나 비하 의도 등 부족한 사실은 Agent가 문맥·정책 조사와 근거에 기록한다.
- 시연 보완을 위해 전역 공백 제거·부사 삭제·기존 예외 삭제로 정규화 의미를 넓히지 않는다.
  기존 정규화는 URL·개인정보·도배 동일 문장 비교에도 쓰이므로 후보 전용 비교와 분리 여부를 검토한다.
- 정상 지명·기관명, 일반 비판(예: `서비스 수준이 너무 낮아`), 인용·제지, 공백·부사 변형을
  회귀 사례에 포함한다. 후보가 된 인용·비판의 최종 판단도 운영자 흐름으로 검증한다.
- 실제 변경 시 후보 사전·정규화·접수 규칙 중 바뀐 구성요소의 버전을 기록하고 과거 사건에 소급하지 않는다.
  이번 작업에서는 사전·정규화 코드·테스트를 수정하지 않는다.

### 2.3 추가 접수 계약의 경계와 미정 사항

- BE가 접수 시 동결한 프로필로 추가 조사 여부를 정하고, 사건 생성·마스킹 snapshot·Outbox를 맡는다.
  Agent는 전달받은 후보의 문맥·정책 조사, 구조화된 근거 기록과 판정 제출을 맡는다.
- 추가 후보는 기존 CONTEXT 사건·판정 제출·운영자 결정을 재사용하는 방향이다.
  위반 확정·HIDE·TIMEOUT·별도 KICK 승인 흐름을 우회하지 않는다.
- 원래 필터 결과와 최종 접수 사유를 구별해 재현 가능하게 보존해야 한다.
  PASS 확대 접수의 filterResult·handlingRoute·ruleId·matchingTags 표현, 후보 출처와
  구조화 HARASSMENT 근거 필수 조건은 BE 계약 보완 시 확정한다. 기존 ATTACK_TERM을
  탐지하지 않은 PASS에 임의로 붙이거나 새 enum·필드를 이 문서만으로 확정하지 않는다.
- **가시성·검토 부담은 구현 전 확인이 필요하다.** 기존 CONTEXT를 그대로 재사용하면
  엄격의 원래 PASS도 HELD가 되고 AI 정상 제안만으로 공개할 수 없어 운영자 결정이 필요하다.
  엄격의 정상 채팅까지 모두 이 흐름으로 처리할지 합의한 뒤 명세에 고정한다.
  PUBLIC 상태 조사나 Agent 자동 정상 공개를 채택하려면 별도 정책·계약 합의가 필요하며
  이번 변경에서 묵시적으로 허용하지 않는다.
- 추가 검사·접수·Outbox 장애나 용량 초과를 정상 PASS·조사 완료로 조용히 처리하지 않는다.
  오류·재시도·중복 사건 방지·과부하 동작은 가시성 합의와 함께 BE 계약으로 확정한다.

## 3. 프로필 정의 — 합의된 요구사항

| 정책 조항 | 엄격 `STRICT` | 보통 `STANDARD` | 자유 `RELAXED` |
|---|:---:|:---:|:---:|
| CP-2.2 문맥 판단의 오탐 예외 | 제외 | 적용 | 적용 |
| CP-3.1 인신공격의 판단 범위 | 적용 | 적용 | 적용 |
| CP-3.2 특정 대상 괴롭힘 | 적용 | 적용 | 적용 |
| CP-3.3 집단 대상 비하·배제 | 적용 | 적용 | 제외 |

### 3.1 엄격

HARASSMENT 판단에 CP-2.2의 예외를 적용하지 않는다.
다만 **예외 제외 자체가 위반의 충분조건은 아니다.**

- CP-3.1의 일반 비판·대상 추정만으로 확정하지 않는 원칙은 유지한다.
- CP-3.2는 식별 가능한 대상과 공격 표현이 확인되어야 한다.
- CP-3.3은 대상 집단과 열등 단정·배제 표현이 확인되어야 한다.
- 핵심 사실이 부족하거나 충돌하면 `NEEDS_REVIEW`로 처리한다.

따라서 인용·농담이라는 형식만으로 면제하지 않지만, 해당 형식이라는 이유만으로
모두 위반으로 판단하지도 않는다.

### 3.2 보통

CP-2.2의 정상 예외를 확인하고, CP-3.1·3.2·3.3에 따라 판단한다.
이는 **신규 v3.3 계약의 기본 프로필**이며, CP-3.3이 없는 구 정책과 동일하다는 뜻은 아니다.

### 3.3 자유

CP-2.2·3.1·3.2를 적용하며 CP-3.3은 적용하지 않는다.

- CP-3.3만으로 성립하는 집단 비하·배제를 HARASSMENT 위반 근거로 사용하지 않는다.
- 특정 개인을 향한 공격도 독립적으로 확인되면 CP-3.2로 판단할 수 있다.
- CP-3.3 비적용을 우회하기 위해 같은 사실을 CP-3.2로 재분류하지 않는다.
- 조항 비적용 자체를 근거 부족으로 취급해 일괄 `NEEDS_REVIEW`로 보내지 않는다.
- 다른 적용 조항의 요건이나 사실관계가 불확실한 경우에는 검토 필요로 처리한다.

적용 가능한 다른 위반 근거가 없고 사실관계가 충분하면 해당 프로필 기준 정상으로
판단한다. 다만 CONTEXT 사건은 AI 정상 제안만으로 공개하지 않고 기존 운영자 결정을 따른다.

### 3.4 프로필과 정책 본문의 우선순위

정책 CP-7.2에 프로필 적용표의 우선순위를 명시하고, CP-2.2·CP-3.3의
상호 참조도 같은 규칙을 따르게 한다.

> HARASSMENT 판단에서는 방송별 프로필의 조항 적용표를 따른다.
> 엄격 프로필에서는 CP-3.3 내부의 CP-2.2 예외 참조도 적용하지 않는다.
> 프로필은 각 위반 조항의 대상·행위·증거 요건을 대체하지 않는다.

**CP-2.2 제외는 HARASSMENT 평가에만 적용한다.**
사칭·개인정보 판단에서는 모든 프로필에서 기존 CP-2.2 적용을 유지한다.
한 메시지에서 여러 위험 유형을 평가할 때에도 유형별 적용 범위를 분리한다.

## 4. 사용자 경험

### MVP

- Phase 2 활성 신규 방송은 `STANDARD`로 시작하고, 이후 플랫폼 관리자만 변경
- 플랫폼 관리자는 프로필 조회·변경, 방송 소유자·담당 moderator는 조회만 가능
- 변경 이후 새로 접수되는 메시지부터 적용된다는 안내
- 엄격은 PASS까지 전량 조사(처리 지연·검토량 증가), 보통·자유는 의심 후보 선별이라는 차이 안내
- 사건 검토 화면에 당시 프로필·적용 조항 표시
- 변경 주체·시각·이전 값·변경 값 기록

단계 설명은 “전체 채팅 규제 수준” 대신 **“비방·괴롭힘 판단 기준”**으로 표시한다.
자유 설명에는 집단 대상 조항 CP-3.3을 적용하지 않는다는 차이를 명시한다.
엄격의 접수 범위 확대와 조항 예외 제외는 별도 설명하며 “품질 보장”으로 표시하지 않는다.

### 제외

상세 슬라이더, 임의 조항 선택, 사용자 작성 프롬프트, 자동 강도 조정,
욕설·도배·링크·개인정보 설정, 제재 기간·강퇴 조건 조정.

## 5. 적용 시점과 불변성

**설정 변경 후 새로 접수되는 메시지부터 적용하고, 기존 사건은 당시 설정을 유지한다.**

1. BE는 메시지 접수 시 적용할 설정 revision을 결정·보존한다.
   이 프로필은 추가 조사 대상 선정에도 사용하며, 비동기 검사 시 현재 설정으로 다시 고르지 않는다.
2. 사건 생성 시 해당 revision의 프로필을 증거 snapshot에 동결한다.
3. 비동기 사건 생성은 접수 시 보존한 참조를 사용하며 최신 설정을 다시 선택하지 않는다.
4. 같은 사건에 서로 다른 프로필 revision의 대상 메시지를 혼합하지 않는다.
5. 설정 변경과 접수가 경합하면 DB 트랜잭션의 명확한 직렬화 기준으로 revision을 결정한다.
6. 설정 rollback은 과거 row 수정이 아니라 새 revision 생성으로 처리한다.

예:

```text
revision 3 / STRICT → 사건 A 생성
설정 변경 → revision 4 / RELAXED → 사건 B 생성

사건 A: 조사·재시도·Worker 교체·승인 재개 모두 STRICT 유지
사건 B: RELAXED 적용
```

설정 변경은 과거 위반·제재를 취소하거나 기존 사건을 자동 재평가하지 않는다.
긴급 정책 변경·과거 사건 재평가는 일반 프로필 변경과 별도 절차로 다룬다.

## 6. 데이터·API 계약

API 경로·요청·응답·권한·revision·오류·구조화 근거는 BE #90에서 결정하며 FE·Agent가 따른다.
원본은 위 BE 계약·OpenAPI이며, 이 절은 소비자 변경 요약이다. 명세 확정은 업무 로직 구현 완료가 아니다.

### 6.1 버전 구분

| 필드 | 의미 |
|---|---|
| `policyVersion` | 정책 문서 버전. 신규 프로필 계약은 `v3.3`, 기존 사건은 `v3.1`/`v3.2` |
| `evidenceSchemaVersion` | 증거 형식. 기존은 생략 또는 `1`, 신규 프로필 계약은 `2` |
| `profileVersion` | 세 프로필의 조항 매핑·해석 규약 버전 |
| `settingsRevision` | 방송별 설정 변경 순번 |
| `filterVersion` | 후보 사전·정규화·접수 규칙의 재현에 쓰는 구현 버전. 정책/프로필 버전과 구분 |

BE #90에서 신규 정책 버전은 `v3.3`, 프로필 버전은 `harassment-profile-v1`로 결정한다.
프로필 규칙을 정책에 반영한 뒤 승인 커밋과 본문 해시를 고정한다.
BE의 A-27·A-28에 기존 v3.2 활성화가 기록돼 있으므로 같은 정책 버전을 덮어쓰지 않는다.
같은 프로필 이름의 조항 매핑·해석 규칙이 변경되면 기존 정의를 덮지 않고
새 `profileVersion`을 발행한다.
지원 가능한 policy/profile 조합은 서버에서 명시적으로 관리한다.

Phase 2 활성 신규 방송의 초기값은 `STANDARD`, `settingsRevision`은 `1`이다.
실제 설정 변경마다 revision을 증가시키며, 기존 방송·사건은 자동 전환하지 않는다.
정책 버전도 메시지 접수 시 해당 방송의 적용 기준으로 보존하여, 전역 기본값 변경이
기존 방송의 새 메시지에 신규 정책을 자동 적용하지 않도록 한다.

### 6.2 사건 snapshot

```json
{
  "policyVersion": "v3.3",
  "evidenceSchemaVersion": 2,
  "harassmentProfile": {
    "level": "STRICT",
    "profileVersion": "harassment-profile-v1",
    "settingsRevision": 3
  }
}
```

- 기존 case/live/snapshot 식별자와 함께 보존한다.
- 프로필 매핑은 버전이 있는 서버 정의를 사용하며 클라이언트가 조항 목록을 지정하지 않는다.
- 과거 정의를 보존해 동일 snapshot을 같은 기준으로 해석할 수 있어야 한다.
- `policyVersion`은 기존 snapshot 필드이며 프로필 안에 중복 저장하지 않는다.
- 신규 증거의 schemaVersion=2와 프로필은 필수다. 저장된 사건의 버전으로 검증하며
  요청 필드 생략으로 legacy 경로를 선택할 수 없다.

판정 제출에도 snapshot과 동일한 `harassmentProfile`을 포함한다.
BE는 `snapshotId`, `evidenceVersion`, `policyVersion`과 프로필의 level·버전·revision을
대조하고 불일치는 409로 거절한다. 신규 계약에서 필수 필드 누락·미지원 값은
명시적으로 거절하며 임의 기본값으로 보완하지 않는다.
동일 사건의 동일 판정 재전송은 기존 결과를 반환한다.
기존 정책 사건은 기존 계약으로 처리하고 신규 프로필을 소급하지 않는다.

### 6.3 설정 API

| API | 역할 |
|---|---|
| `GET /api/lives/{liveId}/harassment-settings` | 현재 프로필·revision·변경 시각 조회 |
| `PUT /api/lives/{liveId}/harassment-settings` | 프로필 변경 |

권한 적용:

| 요청자 | GET 조회 | PUT 변경 |
|---|:---:|:---:|
| 플랫폼 관리자 (`PLATFORM_ADMIN`) | 허용 | 허용 |
| 방송 소유자(스트리머) | 해당 방송만 허용 | 금지 |
| 해당 방송의 담당 moderator | 해당 방송만 허용 | 금지 |
| 그 외 사용자 | 금지 | 금지 |

인증된 사용자라도 권한이 없으면 요청을 거절한다. UI에서 변경 기능을 숨기는 것과
별개로 BE가 매 요청의 권한을 검증하며, 소유자나 moderator의 변경 요청은 같은 값
변경·동일 요청 재전송이어도 허용하지 않는다.

변경 요청 예:

```json
{
  "clientRequestId": "UUID",
  "expectedSettingsRevision": 2,
  "harassmentLevel": "STRICT"
}
```

- 응답 data 필드는 `liveId`, `policyVersion`, `profileVersion`, `harassmentLevel`,
  `settingsRevision`, `changedAt`이며 기존 `{data, traceId}` envelope를 사용한다.
  `changedAt`은 초기 생성 또는 마지막 실제 변경 시각이며 같은 값 변경에는 유지한다.
- 신규 revision 충돌은 409 `STALE_VERSION`과 기존 `currentVersion`으로 현재 revision을
  전달한다. 같은 ID의 다른 본문은 409 `IDEMPOTENCY_CONFLICT`, 종료 방송 신규 변경은
  409 `LIVE_ENDED`, 잘못된 입력은 400 `VALIDATION_FAILED`, 권한 없음은 403 `FORBIDDEN`이다.
  미활성 기존 방송에는 설정을 생성하지 않고 404 `NOT_FOUND`를 반환한다.
- 변경 권한은 플랫폼 관리자(`PLATFORM_ADMIN`)에게만 부여한다.
  방송 소유자(스트리머)와 담당 moderator는 조회만 허용하며 방송 소유권으로
  변경 권한을 부여하지 않는다. UI의 “스트리머” 표기를 관리자 권한으로 취급하지 않는다.
  FE 수정 UI는 기존 `Me.role == PLATFORM_ADMIN`으로 제한하고 방송별 조회는 BE가 검증한다.
  `Me`나 #88의 capabilities를 중복 확장하지 않으며 `DECIDE`·`RAW_TEXT`와 독립적이다.
- 종료된 방송의 설정은 변경할 수 없다.
- 같은 값으로 변경하면 revision을 증가시키지 않는다.
- 동일 요청 재전송은 동일 결과를 반환하고 revision을 다시 증가시키지 않는다.
  현재 revision 검사보다 기존 요청의 멱등성 확인을 먼저 수행해, 이후 다른 변경이
  있었더라도 이미 완료된 요청의 재전송에는 원래 결과를 반환한다.
- 같은 요청 ID에 다른 본문은 409 멱등성 충돌로 거절한다.
- 새로운 요청의 오래된 `expectedSettingsRevision`은 같은 값 변경이어도 409로 거절한다.
- 허용하지 않은 level·필드·정책 조합은 명시적 계약 오류로 거절한다.
- Phase 2 활성 신규 방송 생성 시 최초 프로필과 revision 저장을 함께 처리한다.

저장 구조는 방송별 현재 revision 참조와 수정 불가능한 revision 이력으로 구성한다.
업무 상태는 MCP·Agent 프로세스 메모리가 아니라 BE DB가 정본이다.

## 7. 실행 흐름과 책임

```text
플랫폼 관리자 UI → BE 설정 API → 방송별 설정 revision 저장
방송 소유자·담당 moderator UI → BE 설정 조회 API (변경 불가)

채팅 접수 → 적용 revision 보존 → 기존 BE 필터
 → 기존 확정/조사 경로 우선 유지
 → PASS이면 STRICT만 추가 조사 접수, STANDARD/RELAXED는 PUBLIC·Agent 미호출
 → 기존 사건/증거 snapshot에 프로필 동결
 → 기존 Outbox → Agent Inbox → Graph Worker
 → Business MCP 사건 조회로 동결 프로필 수신
 → 프로필 검증·HARASSMENT 적용 조항 결정
 → 정책 원문 조회·조사·판정 검증
 → 실제 BE 판정 제출
 → 기존 CONTEXT 결정·별도 KICK 승인/재검증/실행
```

### Backend

- 설정 저장·플랫폼 관리자 전용 변경 권한·방송별 조회 권한·revision·멱등성·감사 기록
- 메시지/사건에 적용 프로필 결합
- 동결 프로필에 따른 STRICT의 PASS 추가 접수·기존 CONTEXT 재사용 계약 보완
- 시연 누락 표현의 후보 사전·정규화 보완 검토, 원 필터 결과와 접수 출처 구분
- snapshot과 조사 결과의 프로필 참조 일치 검증
- fallback·승인·조치에서도 사건의 동결 기준 보존
- 기존 필터의 경로 우선순위·다른 위험 유형·위반 확정·제재 규칙 유지

### Business MCP — Backend 2/MCP 연결 범위

- 기존 `get_moderation_case` 응답에 사건의 프로필 snapshot 전달
- 기존 인증·오류 계약 유지
- 별도 현재 설정 조회를 조사 기준으로 사용하지 않음
- 설정 변경 MCP 도구는 추가하지 않음. 관리 UI의 인증된 BE API로 변경

### Agent

- case loader에서 profile 및 지원하는 policy/profile 조합 검증
- State·checkpoint에 동결 프로필 보존
- 공통 조사 지침과 프로필별 조항 적용 지침을 조립
- BE에서 받은 추가 후보도 문맥·정책 조사와 근거를 기록하며 정상·불확실 가능성을 보존
- PHISHING·PII의 예외 판단에는 HARASSMENT 설정을 전파하지 않음
- 판정에 적용 프로필 참조를 포함해 BE가 사건과 대조할 수 있게 계약 확장
- 승인 재개 시 최신 설정으로 덮어쓰지 않고 기존 snapshot과 일치 확인

TaskEnvelope 확장은 필수가 아니다. 기존 snapshotId가 프로필까지 불변으로 결합하고
intake dedupe·재개 검증이 이를 보장하는지 확인한 뒤, 필요할 때만 참조 필드를 추가한다.

### 운영자 UI

- 플랫폼 관리자에게만 현재 프로필 선택·변경과 충돌 알림 제공
- 방송 소유자·담당 moderator에게는 현재 프로필을 조회 전용으로 표시하고,
  방송 시작 요청에 임의 프로필을 넣어 변경 권한을 우회하지 않음
- 변경 이력 및 변경 이후 새로 접수되는 메시지부터 적용됨을 안내
- 검토 화면에 사건 당시 프로필·적용 조항·판정 근거 표시
- 방송의 현재 설정과 사건 당시 설정을 분리하고, 과거 사건의 누락 필드를
  현재 설정이나 `STANDARD`로 보완하지 않음
- 응답 유실 재전송은 같은 요청 ID·본문을 유지하고, revision 충돌은 최신 설정을
  조회한 뒤 사용자 재확인을 거침. 자동 덮어쓰기를 하지 않음

## 8. RAG·프롬프트·결과 검증

BE #90 확정 DTO는 기존 MessageFinding에 `harassmentAssessment`만 추가한다.
내부 필드는 `clauses`다.
각 clause는 `policyId`, `verdict`, `targetStatus`, `conductStatus`,
`targetEvidenceMessageIds`, `conductEvidenceMessageIds`, `exceptionStatus`,
`exceptionEvidenceMessageIds`를 가진다.
요건 상태는 MET/NOT_MET/UNKNOWN, 예외 상태는
NOT_APPLICABLE/APPLIES/DOES_NOT_APPLY/UNKNOWN이다.
STRICT/STANDARD는 CP-3.2·CP-3.3 각각 한 번, RELAXED는 CP-3.2만 평가한다.
STRICT 예외는 NOT_APPLICABLE, 근거는 동일 마스킹 snapshot의 메시지 UUID만 사용한다.
예외는 조항별로 기록하며 집단 발언 인용 예외가 별도 개인 공격을 면제하지 않는다.
HARASSMENT category·조항 또는 ATTACK_TERM이 있는 신규 사건에 필수이며 다른 유형에
일괄 요구하지 않는다. 세부 조건·오류와 서비스 검증 경계는 BE 계약을 따른다.
이는 기존 BE #90 계약 기준이다. STRICT의 PASS 추가 접수에는 ATTACK_TERM이 없을 수 있으므로,
이 후보의 구조화 근거 필수 조건은 §2.3 접수 출처 계약과 함께 보완해야 한다.

브라우저 강퇴 카드의 프로필은 `evidenceCaseId`(basisCaseIds 마지막)의 표시 증거 기준이다.
검토에 연결된 기존 caseId나 전체 강퇴 근거 집합의 단일 프로필로 해석하지 않는다.

프로필은 정책 원문을 수정하거나 RAG 색인에서 조항을 삭제하는 방식으로 구현하지 않는다.
정책 원문은 버전별로 유지하고, 서버가 계산한 **적용 계획**을 조사에 함께 전달한다.

- 공통 지침과 프로필별 적용표를 분리하여 전체 프롬프트 세 벌의 중복을 피한다.
- 검색 결과에 비적용 조항이 포함되어도 이를 위반 근거로 사용하지 않는다.
- CP-3.1은 제한 원칙이며 그 자체를 독립 위반 사유로 취급하지 않는다.
- CP-2.2는 예외 조항이며 그 자체가 위반 사유가 아니다.
- 자유에서 CP-3.3을 HARASSMENT 위반 근거로 제출하면 다른 조항이 함께 있어도
  계약 위반으로 거절한다. 독립적인 개인 공격은 CP-3.2 근거로 별도 판단한다.
- 엄격에서 HARASSMENT 정상 판정의 근거로 CP-2.2 면제를 적용하지 않는다.
- 비적용 조항을 다른 조항으로 우회 적용하는지 비교 평가로 확인한다.

조항 ID 검사만으로 의미적 정확성을 보장할 수 없다. 위 BE 구조화 근거의 요건·예외 상태,
증거 UUID·조항·category 일치를 검증하고 실제 의미적 정확성은 별도 비교 평가로 확인한다.
자유 텍스트 사유만 검사하는 방식으로 검증을 대신하지 않는다.

## 9. 오류·호환·출시

- 새 프로필 계약에서 설정 누락·손상·미지원 버전이면 임의 기본값으로 대체하지 않는다.
- 재조회 가능한 일시 장애와 계약 불일치를 구분하고, 명시적 오류 또는 기존 검토 필요
  경로로 처리한다. 근거 없는 위반 확정·자동 공개는 하지 않는다.
- 구 사건은 기존 정책 경로로 처리하며 신규 프로필을 소급 삽입하지 않는다.
- 신규 기능 활성 방송의 초기 기본값은 `STANDARD`, 최초 revision은 `1`이다.
- `STANDARD`는 승인된 v3.3 적용을 전제로 하며 구 정책의 무조건적인 대체값이 아니다.
- 구 Agent가 신규 snapshot 필드를 무시한 채 조사하지 않도록 지원 버전·배포 순서를 검증한다.
- 계약 소비자/검증 준비 → BE 생산 지원 → 선택 방송 활성화 순서로 배포한다.
- 기능 플래그 기본 OFF로 시작하고, 검증 후 신규 방송에만 활성화한다.
  rollback 시 새 방송의 기능 활성화를 중단하며 기존 방송·사건을 자동 전환하지 않는다.
  이미 생성된 새 정책 사건을 처리할 호환 Worker는 소진까지 유지한다.

## 10. 검증 계획과 완료 기준

### 정책 비교 평가

| 시험군 | 기대 조건 |
|---|---|
| CP-2.2 예외와 공격 요건이 함께 검토되는 사례 | 엄격은 예외 미적용, 보통/자유는 적용. 성립 요건 없이 엄격 위반을 강제하지 않음 |
| 일반 비판·대상 추정에 그치는 사례 | 모든 프로필에서 CP-3.1 보호 |
| 명확한 특정 대상 공격 | 모든 프로필에서 CP-3.2 적용, 보통/자유의 예외 해당 여부 별도 검토 |
| CP-3.3에만 해당하는 집단 비하·배제 | 엄격/보통은 적용, 자유는 해당 조항으로 위반 확정하지 않음 |
| 개인 공격과 집단 비하 혼합 | 자유에서도 독립적인 CP-3.2 요건만으로 판단 가능한지 검증 |
| 대상·인용 의도 등 핵심 문맥 부족 | 프로필과 무관하게 불확실성 명시 |
| 사칭·개인정보의 CP-2.2 예외 | HARASSMENT 설정으로 결과가 변하지 않음 |
| 욕설·도배·링크 규칙 | 기존 결과·처리 경로 불변 |

### 후보 접수·정규화 회귀

- 기존 PASS 입력은 STRICT에서 전부 추가 조사 대상으로 접수하고 STANDARD/RELAXED에서는
  기존 후보 신호가 없으면 PUBLIC·Agent 미호출인지 확인한다.
- 욕설·링크 확정, 도배·개인정보·기존 CONTEXT가 STRICT 추가 접수로 덮이거나 중복 생성되지 않는지 확인한다.
- 시연 누락 두 사례와 어형·부사·공백 변형의 후보화 및 정상 지명·일반 비판·인용 오탐을 검수한다.
- 후보화 결과와 정책 판정 기대값을 분리한다. 자유에서 후보가 전달됐다는 이유만으로 CP-3.3을 적용하지 않는다.
- 설정 변경과 추가 검사·접수가 경합해도 접수 당시 revision과 전달 범위를 유지하는지 확인한다.
- 가시성 합의 후 HELD/PUBLIC·운영자 결정 전후 공개·TIMEOUT·KICK 경계와 장애·재시도·중복 방지를 검증한다.
  이 접수 시험은 아래 정책 평가셋 240개 기대 결과와 별도로 준비하며 이번 작업에서 만들지는 않는다.

검수된 입력별로 세 프로필의 기대 판정·적용 조항·근거를 정의한다.
프롬프트 문구 확인이나 조항 ID 일치만으로 통과 처리하지 않는다.

### 검수 평가셋과 출시 기준

HARASSMENT 입력 60건을 다음 6개 군에 각 10건씩 배정하고,
세 프로필로 평가하여 기대 결과 180개를 작성한다.

1. 예외·인용·농담
2. 일반 비판·비공격 표현
3. 특정 개인 공격
4. 집단 비하·배제
5. 개인·집단 공격 혼합
6. 문맥 부족·불확실

다른 유형 회귀 입력은 욕설·도배·피싱·개인정보 각 5건, 총 20건을
세 프로필로 평가하여 기대 결과 60개를 작성한다.
전체 기대 결과는 240개이며, 각 사례에 판정·적용 조항·필수 근거·기대 차이를
명시하고 정책 담당자와 BE/Agent 담당자가 공동 검수한다.
평가셋 작성·공동 검수는 후속 작업이며 이번 정책·API 설계 문서 정리 범위에 포함하지 않는다.
아래 기준은 후속 검증·출시 판단에 적용하며, 평가셋이 아직 없다는 이유로
합의된 API 설계 반영을 미루지는 않는다.

출시 판단 기준은 다음과 같다.

- 통제 모델 계약·경로 시험: 100% 통과
- 선택한 실제 모델의 기대 판정 일치율: 전체 및 각 프로필별 90% 이상
- 비적용 조항으로 위반 판정, 다른 유형 기준 변경, 승인 우회: 각각 0건
- STRICT의 CP-2.2 예외 미적용은 구조화된 판단 근거와 비교 평가로 검증하며,
  사유 문자열 검사로 대체하지 않음
- 실제 모델 미검증이면 통합 기능 검증과 구분하며 운영 판단 품질 통과를 주장하지 않음

### 계약·분산 실행

- 다른 방송 설정 혼입 방지, 권한 없는 변경 거부
- 플랫폼 관리자 변경 허용, 방송 소유자·담당 moderator의 조회 허용 및 변경 거부
- 소유자·moderator의 같은 값 변경·재전송을 통한 권한 우회 거부
- 설정 변경 동시 요청의 revision 충돌
- 설정 변경·메시지 접수 경합 시 revision 누락·혼합 방지
- 동일 요청/사건/판정 재전송의 멱등성
- 조사·승인 대기 중 설정 변경 후 기존 사건 기준 유지
- Worker 강제 종료·lease 회수·checkpoint 재개 후 동일 기준 유지
- 응답 유실·fallback·늦은 결과에서 기존 확정 결과와 조치 효과 보존
- 구/신 계약 혼합 배포에서 설정 누락을 조용히 허용하지 않음

### 관측

프로필별 HARASSMENT 제안 비율, 정상/검토 필요 비율, 운영자 판정 변경 비율,
적용 조항 오류, 조사 지연·실패율을 구분해 관측한다.
기존 후보와 STRICT의 PASS 확대 접수를 구분해 접수량·처리 지연·대기량·비용·운영자 검토량을 측정한다.
조사 범위 차이로 입력 집합이 달라지므로 단순 위반 비율을 프로필 판단 품질로 비교하지 않는다.
로그·지표에는 token·원문 채팅·모델 입력을 추가하지 않는다.

## 11. 개발 순서와 담당 경계

| 단계 | 산출물 | 주 담당 경계 |
|---|---|---|
| 1 | 정책의 프로필 우선순위·버전 확정 | 정책/Agent/BE 공동 |
| 2 | 설정 API·revision·snapshot·판정 제출 및 STRICT PASS 추가 접수·가시성·오류 계약 | BE/Backend 2/MCP/Agent 공동 |
| 3 | 설정 저장·접수 참조·프로필별 전달 분기·후보 보완·사건 snapshot·서버 검증 | BE |
| 4 | 기존 사건 조회의 프로필 전달 | Backend 2/Business MCP |
| 5 | 프로필 검증·조사 지침·결과 검증·checkpoint 재개 | Agent |
| 6 | 시작/변경 UI·사건 기준 표시 | FE |
| 검증 준비 | 240개 기대 결과 작성·공동 검수 (별도 후속 작업, 단계 7 전 완료) | 정책/Agent/BE 공동 |
| 7 | 계약·회귀·실제 BE 공동 시험과 선택 방송 활성화 | 공동 |

단계 1·2를 먼저 합의한 뒤 BE·Agent·FE를 병렬 개발한다.
현재 Phase 2 코드 구현은 중단되어 있으며 위 순서는 재개 후 계획이다.
시연용 사전·정규화 보완은 별도 소규모 변경으로 검수할 수 있지만 이번 문서 수정으로 구현하지 않는다.
신규 Rabbit 큐·Worker 배분 구조·모델 공급자 변경은 이 기능의 선행 조건이 아니다.

### BE 계약 확정 후 후속 작업

1. 승인 v3.3 원문 커밋·본문 해시와 RAG 색인 준비(기존 v3.1/v3.2 보존)
2. 추가 접수의 가시성·운영자 검토 범위·출처 표현·구조화 근거·과부하/오류 계약 공동 확정
   후 BE 명세 보완 및 설정 API·저장·접수 참조·권한·프로필별 전달·snapshot·판정 서비스 검증 구현
3. MCP·Agent의 schema 2·동결 프로필·구조화 근거·checkpoint·승인 재개 구현
4. FE의 설정 조회/변경·409 재확인·사건 당시 프로필·표시 증거 출처 구현
5. 소비자 준비 → BE 생산 지원 → 신규 방송 활성화. rollback은 신규 활성화 중단이며
   기존 schema 2 사건의 BE·Worker·RAG 처리 능력을 유지

평가셋 작성은 위 API 설계 확정과 분리된 후속 작업으로 진행한다.
운영 활성화 전에는 240개 기대 결과 작성·공동 검수와 수치화된 출시 기준 검증을 완료한다.

## 요약

**방송별 HARASSMENT 프로필을 사건에 동결하고, Agent가 해당 프로필의 조항 조합으로
조사한다. 엄격은 기존 PASS까지 전량 조사 대상으로 확대하고, 보통·자유는 의심 후보만
전달한다. 다른 위험 유형과 기존 승인·제재 체계는 바꾸지 않는다.**

엄격은 CP-2.2 제외, 보통은 CP-2.2·3.1·3.2·3.3 적용,
자유는 CP-3.3 제외다. 각 조항의 성립 요건과 불확실성 처리는 모든 프로필에서 유지한다.
Phase 2 코드는 중단 상태이며, STRICT 전량 조사에 따른 가시성·운영자 검토 부담과
BE 접수 계약을 먼저 확정한 뒤 구현을 재개한다.
